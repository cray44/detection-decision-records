# DDR v0.7 — KQL Targets (Microsoft Sentinel + M365D Advanced Hunting)

**Status:** Plan drafted. Awaiting IMPLEMENT signal.
**Decided:** 2026-05-11
**Theme:** Complete the four-SIEM target union (Sigma, Splunk, Elastic, KQL). Add Microsoft Sentinel and M365D Advanced Hunting as native DDR targets, closing the last major gap before schema freeze prep.

---

## Decision

v0.7 adds two new target kinds: `"kql-sentinel"` and `"kql-m365d"`.

Six new models: `KqlSentinelQueryRef`, `KqlSentinelTarget`, `KqlSentinelTuning`, `KqlM365DQueryRef`, `KqlM365DTarget`, `KqlM365DTuning`.
One new exporter: `ddr export-kql` → Kusto `| where not (...)` fragment (works for both target kinds).
Two new canonicalization algorithms: Sentinel ARM JSON v1, M365D API JSON v1.
Two new examples: example 10 (Sentinel suppress), example 11 (M365D suppress).

Out of scope for v0.7: schema freeze (v0.9/v1.0), `ddr upgrade` migration tooling (v0.8), CI/pre-commit hooks (v0.8), SigmaHQ upstream RFC (v1.0), any UI.

**Why both at once:** Sentinel and M365D both use Kusto Query Language as their query language. The tuning field (`kusto_filter`), export format (`| where not (...)`), and CLI command (`export-kql`) are identical. Shipping them together avoids a half-finished KQL story and keeps the target union clean.

**Why `kusto_filter`, not `kql_filter`:** v0.6 uses `kql_filter` for Elastic's Kibana Query Language, which is colloquially called "KQL" but is distinct from Kusto. Using `kusto_filter` for Sentinel/M365D avoids the KQL ambiguity and makes the field self-documenting.

**Roadmap position:** After v0.7, all four target kinds in the v1.0 North Star are implemented. v0.8 focuses on QoL and CI integration. v0.9 locks the schema for the v1.0 freeze.

## 7-Section Plan (locked)

### 1. Refined Goal & Success Criteria

A detection engineer can:

- Write a DDR for a noisy Sentinel Analytics Rule using `ddr new --target kql-sentinel rule.json --output my_suppression.yml`.
- Write a DDR for a noisy M365D custom detection using `ddr new --target kql-m365d detection.json --output my_suppression.yml`.
- Record the FP suppression as a `kusto_filter` clause: `InitiatingProcessParentFileName =~ "msiexec.exe"`.
- `ddr validate ddr.yml` → passes.
- `ddr export-kql ddr.yml` → outputs a Kusto `| where not (...)` fragment in a `.kql` file; engineer pastes it into the rule's KQL query.
- `ddr refresh-hash ddr.yml` → recomputes `content_hash` from the rule JSON on disk.
- `ddr list detections/` → shows `kql-sentinel` or `kql-m365d` in the `TARGET` column, correct ref count.
- All v0.1–v0.6 records validate unchanged.

Success = an engineer working in Sentinel or M365D can suppress a FP class, export a Kusto exclusion fragment, and track expiry — without touching Sigma tooling.

### 2. Proposed Changes / Feature Breakdown

**Models (`src/ddr/models/record.py`):**

`KqlSentinelQueryRef` — new model:
```python
class KqlSentinelQueryRef(BaseModel):
    model_config = ConfigDict(extra="forbid")

    rule_id: str  # ARM resource name or GUID assigned by Sentinel
    name: str
    workspace: str | None = None  # Log Analytics workspace name (optional context)
    content_hash: str | None = Field(default=None, description="sha256 of canonicalized rule JSON")
    path_or_url: str | None = None  # path to ARM export JSON or Sentinel API response JSON
    source: RuleSource

    @field_validator("content_hash")
    @classmethod
    def validate_hash_format(cls, v: str | None) -> str | None:
        if v is not None and not _CONTENT_HASH_RE.match(v):
            raise ValueError("content_hash must be 'sha256:<64 lowercase hex chars>'")
        return v
```

`KqlSentinelTarget` — new model:
```python
class KqlSentinelTarget(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["kql-sentinel"] = "kql-sentinel"
    query_refs: list[KqlSentinelQueryRef] = Field(..., min_length=1)
```

`KqlSentinelTuning` — new model:
```python
class KqlSentinelTuning(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["kql-sentinel"] = "kql-sentinel"
    filter_title: str | None = None
    filter_description: str | None = None
    kusto_filter: str = Field(..., description="Kusto WHERE clause for FP exclusion")

    @field_validator("kusto_filter")
    @classmethod
    def not_blank(cls, v: str) -> str:
        if not v or not v.strip():
            raise ValueError("kusto_filter must not be empty or whitespace")
        return v
```

`KqlM365DQueryRef`, `KqlM365DTarget`, `KqlM365DTuning` — same structure as Sentinel counterparts but with `kind: Literal["kql-m365d"]`. `KqlM365DQueryRef` has `table` (str | None) instead of `workspace` to capture the primary Advanced Hunting table (e.g., `DeviceProcessEvents`).

**Updated unions:**

`Target` discriminator: add `KqlSentinelTarget` and `KqlM365DTarget`.
`TuningUnion` discriminator: add `KqlSentinelTuning` and `KqlM365DTuning`.

Cross-field validator in `DDRRecord.check_record_constraints`: existing `tuning.kind == target.kind` check covers both KQL kinds automatically — no change needed.

`ddr_version` pattern: `^0\.[1234567]$`.

**Sentinel canonicalization algorithm v1 (`src/ddr/_internal/sentinel_hash.py`):**

Used by `KqlSentinelQueryRef.content_hash`.

Steps:
1. Load JSON from `path_or_url` (local path only; remote URLs skipped).
2. If the top-level object has `"properties"` (ARM resource envelope), extract `obj["properties"]` and process that sub-object. Otherwise use the top-level object.
3. Strip volatile ARM/Sentinel API fields: `etag`, `lastModifiedUtc`, `lastRunTime`, `nextRunTime`, `lastDeploymentStatusMessage`, `lastDeploymentStatus`, `alertRuleTemplateName` (template linkage, not logic), `templateVersion`.
4. Also strip envelope-level fields if present: `id`, `name`, `type`, `systemData`.
5. Sort mapping keys recursively.
6. Serialize to compact JSON: `json.dumps(rule_dict, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`.
7. UTF-8 encode → SHA-256 → `sha256:` prefix.

Rationale: `lastModifiedUtc`, `lastRunTime`, `nextRunTime` change on every rule execution. `etag` changes on every ARM save. Stripping these means `content_hash` tracks rule logic (`query`, `severity`, `triggerOperator`, `triggerThreshold`, `suppressionDuration`, threat intelligence fields), not Sentinel's bookkeeping.

**M365D canonicalization algorithm v1 (`src/ddr/_internal/m365d_hash.py`):**

Used by `KqlM365DQueryRef.content_hash`.

Steps:
1. Load JSON from `path_or_url` (local path only).
2. Strip volatile Defender/Graph API fields: `id`, `createdDateTime`, `lastModifiedDateTime`, `lastRunTime`, `nextRunTime`, `isEnabled` (enabled state is operational, not logic), `createdBy`, `lastModifiedBy`.
3. Sort mapping keys recursively.
4. Serialize to compact JSON → UTF-8 → SHA-256 → `sha256:` prefix.

Rationale: `lastModifiedDateTime` and `lastRunTime` change on every scheduled execution. `isEnabled` toggles without changing rule logic. Stripping them means `content_hash` tracks `queryCondition`, `detectionAction`, `alertTitle`, `severity`, and `mitreTechniques` — the substance of the detection.

**CLI: `ddr new` (update):**

- `--target kql-sentinel` and `--target kql-m365d` added as valid options.
- No extension inference (Sentinel ARM exports are `.json`; M365D API exports are `.json`; ambiguous with Elastic). Explicit `--target` flag required.
- Scaffold extracts `rule_id` and `name` from JSON if parse succeeds. Falls back to placeholder values with `# MANUAL:` comment.
- Tuning block scaffold:
  ```yaml
  tuning:
    kind: kql-sentinel     # or kql-m365d
    filter_title: 'TODO: descriptive filter name'
    kusto_filter: 'TODO: Kusto WHERE clause, e.g. InitiatingProcessParentFileName =~ "msiexec.exe"'
  ```

**CLI: `ddr refresh-hash` (update):**

Sentinel branch: iterates `target.query_refs`. For each ref with a local `path_or_url`, loads JSON and applies Sentinel canonicalization v1. Prints per-ref drift status. Writes updated hashes.
M365D branch: same pattern, applies M365D canonicalization v1.

`--rule` override: same single-ref-only restriction as all other target branches.

**CLI: `ddr validate --strict` (update):**

Drift check iterates `query_refs` for both KQL target kinds (same pattern as Sigma/Splunk/Elastic). Warns per-ref on drift. Warns if ref count > 10.

**CLI: `ddr export-kql` (new command):**

```
ddr export-kql <ddr.yml> [--output <file.kql>]
```

- Validates DDR; exits 1 if `target.kind` is not `"kql-sentinel"` or `"kql-m365d"`.
- Exits 1 with clear error if `decision.kind != "suppress"`.
- Outputs a Kusto exclusion fragment:
  ```kusto
  // DDR: <ddr.title>
  // Rationale: <decision.rationale (first 120 chars)>
  // Expires: <lifecycle.expires_on>
  | where not (<tuning.kusto_filter>)
  ```
- If `--output` is given, writes the fragment to that file; otherwise prints to stdout.
- No MANUAL fallback needed: `kusto_filter` is stored as a raw Kusto expression, not parsed or transformed. The engineer is responsible for its correctness; DDR is governance, not a Kusto parser.

**Naming note:** One command covers both `kql-sentinel` and `kql-m365d` because the output format is identical (Kusto `| where not (...)`). A hypothetical future `export-sentinel-rule` (exporting the full ARM template with the filter baked in) would be distinct.

### 4. Edge Cases & Error Handling

| Case | Handling |
|---|---|
| `export-kql` on `target.kind = "sigma"` or `"splunk"` or `"elastic"` | Exit 1: "this command requires target.kind: kql-sentinel or kql-m365d". |
| `export-kql` on `decision.kind != "suppress"` | Exit 1: "accept-risk and deprecate decisions have no KQL fragment to export". |
| `kusto_filter` contains Kusto functions or complex expressions | No error — stored as-is, emitted as-is. Engineer owns correctness. |
| `path_or_url` is a URL on `refresh-hash` | Skip; print "skipping remote ref — update content_hash manually". |
| `path_or_url` is None on `refresh-hash` | Print "no path_or_url set for ref[n]; skipping". |
| Sentinel JSON has ARM envelope (`"properties"` key) | Extract `obj["properties"]` before hashing. |
| Sentinel JSON has no `"query"` field | Hash what's there; emit no warning (schema may vary by export method). |
| M365D JSON is an array (bulk export) | Use first element; print note "multi-item export — using first detection". |
| `query_refs: []` | Pydantic `min_length=1` → validation error (consistent with all other target kinds). |
| `ddr list` with KQL records | `TARGET` column shows `kql-sentinel` or `kql-m365d`; `REFS` column shows ref count. |
| `ddr new --target kql-sentinel` without a source file | Scaffold with all-placeholder values; no auto-extraction. |

### 6. Sigma Compatibility & Ecosystem Fit

KQL targets are not Sigma-native. Sentinel can ingest Sigma rules via the Sentinel Sigma connector or via pySigma's Sentinel backend (`pysigma-backend-microsoft365defender`), but the resulting Analytics Rule is a KQL resource — it's a deployed Sentinel artifact, not a Sigma file. DDR governance applies at the deployed artifact, not the source Sigma rule. A DDR can reference both: a `target.kind: "sigma"` DDR for the source rule and a `target.kind: "kql-sentinel"` DDR for the deployed Sentinel version. They are separate governance decisions at different layers.

`ddr export-sigma-filter`, `export-splunk`, and `export-elastic-exception` all correctly exit 1 on KQL targets. `export-kql` exits 1 on non-KQL targets. The target-specific export guarantee is maintained.

For the upstream Sigma pitch: v0.7 completes the four-SIEM target union described in the v1.0 North Star. DDR can now govern detection FP decisions across Sigma, Splunk, Elastic, Sentinel, and M365D from a single record format. This is the multi-SIEM governance story that makes DDR interesting as a Sigma-adjacent spec rather than a Sigma-only tool.

### 7. Final Plan Summary

v0.7 adds `target.kind: "kql-sentinel"` and `target.kind: "kql-m365d"` as the fourth and fifth target kinds. Six new models (`KqlSentinelQueryRef/Target/Tuning`, `KqlM365DQueryRef/Target/Tuning`) follow the same plural-refs and discriminated-union pattern established in v0.5 and inherited by v0.6. The field `kusto_filter` is used (not `kql_filter`) to avoid confusion with Elastic's Kibana Query Language. `ddr export-kql` emits a Kusto `| where not (...)` fragment for both target kinds — a paste-in exclusion clause rather than an importable artifact, because neither Sentinel nor M365D has a Kibana-style exception list format. Two canonicalization algorithms strip volatile API/ARM fields before hashing. Two new worked examples (Sentinel red team IP suppression, M365D LOLBin admin suppression). After v0.7, all four SIEM targets in the v1.0 North Star are in place. v0.8 focuses on QoL (CI hooks, `ddr upgrade`, `ddr lint`). v0.9 prepares the schema freeze. v1.0 locks the spec and ships the SigmaHQ upstream RFC.

## Architecture notes

**Why separate `KqlSentinelTuning` and `KqlM365DTuning` instead of one shared `KqlTuning`:** The discriminated-union pattern requires each tuning kind to exactly match its target kind. A shared `KqlTuning` with `kind: "kql"` would not satisfy the cross-field validator (`tuning.kind == target.kind`). Keeping them separate also leaves room for divergence — Sentinel may gain Sentinel-specific tuning fields (e.g., `suppression_duration`) without touching M365D's model.

**Why `kusto_filter` stored as raw string (no parsing):** Elastic's `kql_filter` needed parsing because Kibana exception list `entries[]` are structured objects — a raw KQL string cannot be directly imported into Kibana. Kusto `| where not (...)` is a fragment that gets pasted into a KQL query as-is. Parsing Kusto expressions would add significant complexity for no benefit (the output format doesn't require structured fields). The engineer writes valid Kusto; DDR stores it and emits it.

**Why `workspace` (Sentinel) and `table` (M365D) are optional:** These are contextual, not authoritative identifiers. The `rule_id` is the authoritative key for looking up the rule. `workspace` helps a multi-workspace Sentinel user know where the rule lives; `table` helps an M365D user know which hunting table to look in. Neither affects hashing or export.

**Why one `export-kql` command for two target kinds:** The output format is identical for both. A per-target-kind command (`export-kql-sentinel`, `export-kql-m365d`) would be noise with no benefit. The command validates that `target.kind` is one of the two KQL kinds and exits 1 otherwise.
