# Design Doc — DDR v0.8: Splunk Cloud Support

**Date:** 2026-05-28  
**Author:** Chris Ray  
**Status:** Implemented

---

## Problem

Splunk Cloud engineers have no filesystem access to `savedsearches.conf`. Since v0.3, DDR
required a `.conf` file to compute `query_hash` for Splunk-native targets. Cloud users either
had to skip `query_hash` entirely (losing drift detection) or fake a `.conf` file (error-prone,
non-portable).

## Approach

Extend the existing `splunk` target — no new `target.kind`. Source format is detected from
file content, not extension. The core invariant: **identical SPL produces identical `query_hash`**
regardless of source format, so detections can migrate between Enterprise and Cloud without
hash churn.

### Why file-based only (no live fetch in v0.8)

Live HTTP fetch (`--splunk-host`, `--splunk-token`) was scoped out after review:

1. Brings network I/O, TLS, auth, and redaction into a CLI that has been pure-local since v0.1.
2. The marginal value over `curl … > export.json && ddr new export.json` is small — one
   extra command versus a new failure surface (DNS, certs, 401/403, proxies, XML responses).
3. Checking in the export artifact alongside the DDR gives a stable, auditable snapshot that
   also enables drift detection without re-fetching. This matches the `.conf` Enterprise pattern.

Live fetch is deferred to v0.9 as a dedicated `ddr splunk-fetch` subcommand.

## Hash Identity

`canonicalize_spl` (spec/ddr-v0.4.md §6) was already the right abstraction:

- CRLF→LF normalization covers `\r\n` in JSON strings.
- Backslash-continuation joining covers multi-line `.conf` SPL.
- Whitespace collapse handles indentation variations.

The Cloud parser extracts the raw SPL string from JSON and feeds it directly to
`canonicalize_spl` — no separate normalization pass. The same function, same algorithm,
same hash.

Regression test: `test_hash_identity_conf_vs_cloud_simple` in `tests/test_splunk_cloud.py`
asserts that Example 06's SPL hashes identically from `.conf` and from a fake servicesNS
JSON. This test is a release blocker.

## Content-Driven Dispatch

Auto-detection priority in `_cmd_new_splunk_from_source`:

1. `.conf` extension → Enterprise path.
2. JSON-parseable with `entry[]`, `content`, or `search` key → Cloud path.
3. Otherwise → Enterprise path (conf parser will fail with a clear error).

`--format conf|cloud-json` always overrides. Recommended when sniffing could misfire.

## App Precedence

Parallel to Enterprise path where `infer_app_from_path` extracts app from the `.conf` file
path. For Cloud: `acl.app` is the canonical source; `--app` overrides with a NOTE.

## KQL Bug Fix

`_cmd_new_kql` was called with `source_url=source_url` from `cmd_new` since v0.7.1, but
the function signature did not accept `source_url`. The parameter was silently ignored
(Python would raise `TypeError` if the keyword argument reached the function, but Typer's
runner suppresses it in tests). Fixed in v0.8: `_cmd_new_kql` now accepts `source_url`
and uses `_compute_path_or_url`.
