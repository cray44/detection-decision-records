# DDR v0.6 — Elastic Target

**Status:** Plan drafted. Awaiting IMPLEMENT signal.
**Decided:** 2026-05-08
**Theme:** Add Elastic Security as a native DDR target, inheriting the v0.5 plural-refs pattern from day one.

---

## Decision

v0.6 adds one new target kind: `"elastic"`.

Three new models: `ElasticTarget`, `ElasticQueryRef`, `ElasticTuning`.
One new exporter: `ddr export-elastic-exception` → Elastic Security exception list NDJSON.
One new canonicalization algorithm: Elastic rule JSON hash v1.
One new example: example 09 (Windows Defender AV scanner noise → Elastic suppress).

Out of scope for v0.6: KQL targets (Sentinel, M365D — v0.7), schema freeze (v0.9/v1.0), migration tooling, UI.

**Why this order:** v0.5 locked the plural-refs shape. v0.6 is the first target to inherit it from day one — no coercion shim needed, no back-compat debt. Elastic is a realistic secondary SIEM for detection teams already running Sigma → Elastic via pySigma's Elastic backends; the target model should reflect that operational reality.

---

## 7-Section Plan (locked)

### 1. Refined Goal & Success Criteria

A detection engineer can:

- Write a DDR for a noisy Elastic Security rule (endpoint.events.process, for example) using `ddr new <rule.ndjson>` or `ddr new --target elastic`.
- Record the FP suppression as a `kql_filter` clause: `process.parent.executable : "/usr/bin/chef-client"`.
- `ddr validate ddr.yml` → passes.
- `ddr export-elastic-exception ddr.yml` → outputs a Kibana-importable NDJSON exception list item. Simple single-field KQL conditions emit structured `entries[]`; complex KQL emits a `MANUAL:` warning and the raw KQL in the item's `description`.
- `ddr refresh-hash ddr.yml` → recomputes `content_hash` from the Elastic rule NDJSON on disk.
- `ddr list detections/` → shows `elastic` in the `TARGET` column, correct ref count.
- All v0.1–v0.5 records validate unchanged.

Success = an Elastic-native engineer can suppress a FP class, export an exception item, and track expiry — without touching Sigma tooling.

### 2. Proposed Changes / Feature Breakdown

**Models (`src/ddr/models/record.py`):**

`ElasticQueryRef` — new model:
```python
class ElasticQueryRef(BaseModel):
    model_config = ConfigDict(extra="forbid")

    rule_id: str  # Elastic rule UUID (string, not Python UUID — Elastic uses lowercase hex without hyphens in some versions)
    name: str
    index_pattern: str = Field(..., description="e.g. 'logs-endpoint.events.process-*'")
    content_hash: str | None = Field(default=None, description="sha256 of canonicalized rule JSON")
    path_or_url: str | None = None
    source: RuleSource

    @field_validator("content_hash")
    @classmethod
    def validate_hash_format(cls, v: str | None) -> str | None:
        if v is not None and not _CONTENT_HASH_RE.match(v):
            raise ValueError("content_hash must be 'sha256:<64 lowercase hex chars>'")
        return v
```

`ElasticTarget` — new model:
```python
class ElasticTarget(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["elastic"] = "elastic"
    query_refs: list[ElasticQueryRef] = Field(..., min_length=1)
```

No coercion shim needed — v0.6 is the first Elastic version; no singular-field back-compat required.

`ElasticTuning` — new model:
```python
class ElasticTuning(BaseModel):
    model_config = ConfigDict(extra="forbid")

    kind: Literal["elastic"] = "elastic"
    filter_title: str | None = None
    filter_description: str | None = None
    kql_filter: str = Field(..., description="Raw KQL filter clause (FP condition)")

    @field_validator("kql_filter")
    @classmethod
    def not_blank(cls, v: str) -> str:
        if not v or not v.strip():
            raise ValueError("kql_filter must not be empty or whitespace")
        return v
```

**Updated unions:**

`Target` discriminator: add `ElasticTarget`.
`TuningUnion` discriminator: add `ElasticTuning`.

Cross-field validator in `DDRRecord.check_record_constraints`: existing `tuning.kind == target.kind` check covers Elastic automatically — no change needed.

`ddr_version` pattern: `^0\.[123456]$`.

**CLI: `ddr new` (update):**

- `--target elastic` flag option added.
- When `--rule` is provided and points to an `.ndjson` file, infer `--target elastic` automatically.
- Scaffold extracts `rule_id`, `name`, and infers `index_pattern` from rule NDJSON. Falls back to placeholder values if parse fails.
- Emits `query_refs: [{...}]` (plural, consistent with v0.5).
- Tuning block scaffold:
  ```yaml
  tuning:
    kind: elastic
    filter_title: 'TODO: descriptive filter name'
    kql_filter: 'TODO: KQL filter clause, e.g. process.parent.executable : "/path/to/tool"'
  ```

**CLI: `ddr refresh-hash` (update):**

Elastic branch: iterate `target.query_refs`. For each ref, load NDJSON from `path_or_url`, apply canonicalization algorithm v1, compare to stored `content_hash`. Print per-ref drift status. Write updated hashes.

`--rule` override: same single-ref-only restriction as Sigma/Splunk branches. Multi-ref Elastic DDRs must update `path_or_url` directly.

**CLI: `ddr validate --strict` (update):**

Drift check iterates `query_refs` for Elastic target (same pattern as Sigma/Splunk). Warns per-ref on drift. Warns if ref count > 10.

**CLI: `ddr export-elastic-exception` (new command):**

```
ddr export-elastic-exception <ddr.yml> [--output <file.ndjson>] [--list-id <str>]
```

- Validates DDR; exits 1 if `target.kind != "elastic"`.
- Exits 1 with clear error if `decision.kind != "suppress"` (accept-risk and deprecate have no exception to export).
- Parses `tuning.kql_filter` with a best-effort single-field KQL parser:
  - Pattern: `field.path : "value"` → `{"field": "...", "operator": "included", "type": "match", "value": "..."}`
  - Pattern: `field.path : wildcard*` → `{"field": "...", "operator": "included", "type": "wildcard", "value": "..."}`
  - AND-joined simple conditions → multiple entries (all must match).
  - Anything more complex (OR, NOT, nested parens, functions) → entries left as `[]`, MANUAL warning printed to stderr.
- Outputs one NDJSON line per exception list item (Kibana 8.x import format).
- Output includes raw `kql_filter` in the item's `description` regardless of parse success, so reviewers always see the source intent.
- `--list-id` sets the exception list `list_id`; defaults to `"ddr-exceptions"`.
- Prints `# MANUAL: Review and complete entries[] before importing into Kibana` when KQL was too complex to parse.

**Elastic canonicalization algorithm v1 (`src/ddr/hashers/elastic.py`):**

Used by `target.query_refs[n].content_hash` to hash an Elastic detection rule JSON/NDJSON file.

Steps:
1. Load NDJSON: if file contains multiple lines, take the first non-empty line that is a JSON object with `"type": "rule"` or that has a `"rule"` key (Kibana export wraps the rule).
2. Extract the rule dict: if the top-level object has a `"rule"` key, use `obj["rule"]`; otherwise use the top-level object.
3. Strip volatile fields that Kibana updates on import/export without changing rule logic: `created_at`, `updated_at`, `created_by`, `updated_by`, `revision`, `version`, `id`, `immutable`, `related_integrations`, `required_fields`, `setup`.
4. Sort mapping keys recursively (same approach as Sigma canonicalization).
5. Serialize to compact JSON: `json.dumps(rule_dict, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`.
6. UTF-8 encode → SHA-256 → `sha256:` prefix.

Rationale for stripping volatile fields: `revision` increments on every enable/disable toggle. `version` increments on Elastic prebuilt rule updates. Hashing these would cause spurious drift every time Elastic updates its prebuilt rule library.

### 4. Edge Cases & Error Handling

| Case | Handling |
|---|---|
| `export-elastic-exception` on `target.kind != "elastic"` | Exit 1: "this command requires target.kind: elastic". |
| `export-elastic-exception` on `decision.kind != "suppress"` | Exit 1: "accept-risk and deprecate decisions have no exception to export". |
| `kql_filter` contains OR / NOT / nested parens | MANUAL warning to stderr; `entries: []` in output; raw KQL in `description`. |
| `kql_filter` is a simple AND of field : value conditions | Structured `entries[]` emitted; no MANUAL warning. |
| `path_or_url` is a URL (http/https) on `refresh-hash` | Skip hash computation; print "skipping remote ref — update content_hash manually". |
| `path_or_url` is None on `refresh-hash` | Print "no path_or_url set for ref[n]; skipping". |
| NDJSON file has multiple rule objects | Use first object with `"type": "rule"` or warn and use first non-empty line. |
| Elastic rule NDJSON has `"rule"` wrapper key | Strip wrapper, hash `obj["rule"]`. |
| `rule_id` is a UUID with or without hyphens | Accept both; store as provided. |
| `ddr new` with NDJSON that fails to parse | Fall back to placeholder `rule_id`, `name`, `index_pattern`; emit `# MANUAL:` comment in scaffold. |
| `query_refs: []` | Pydantic `min_length=1` → validation error (same as Sigma/Splunk). |
| `ddr list` with Elastic records | `TARGET` column shows `elastic`; `REFS` column shows count of `query_refs`. |

### 6. Sigma Compatibility & Ecosystem Fit

The Elastic target is Sigma-adjacent, not Sigma-native. Many teams convert Sigma rules to Elastic via pySigma's `pysigma-backend-elasticsearch`. A DDR with `target.kind = "elastic"` can reference the *Elastic rule* that resulted from that conversion, not the source Sigma rule. This is intentional: the DDR governance applies at the point where FPs are suppressed — in the deployed SIEM, against the deployed rule.

`ddr export-sigma-filter` correctly exits 1 on Elastic targets (same as Splunk). The Elastic exporter is its own command and its own format.

The Elastic exception list format (NDJSON) is well-established in Kibana 8.x. Importing via Kibana UI (Security → Rules → Exceptions → Import exception list) or via the Kibana Exceptions API is documented. DDR's export targets that workflow.

For the upstream Sigma pitch: having DDR cover Sigma → Elastic as a lifecycle pattern (suppress FPs in Elastic Security using DDR records that reference the converted rule) is a concrete differentiator. Example 09 demonstrates the full chain.

KQL targets (Sentinel `KqlSentinelQueryRef`, M365D) are v0.7. Those inherit the same `query_refs: list[...]` pattern and the same `kql_filter` approach; the exporter format differs (Sentinel hunting queries, M365D custom detections).

v0.6 adds `target.kind: "elastic"` with `ElasticTarget`, `ElasticQueryRef`, and `ElasticTuning`. The plural-refs pattern from v0.5 is inherited from day one — no coercion shim. `ElasticTuning.kql_filter` stores a raw KQL filter clause. `ddr export-elastic-exception` outputs a Kibana 8.x-importable NDJSON exception list item: simple AND/field:value KQL is parsed into structured `entries[]`; complex KQL emits a `MANUAL:` warning and preserves the raw KQL in `description`. Example 09 demonstrates Elastic suppress against a noisy prebuilt rule. No existing model or command changes behavior. ~20 new tests. ## Architecture notes

**Why `rule_id: str` not `rule_id: UUID`:** Elastic rule IDs are UUIDs but some Elastic API responses omit hyphens, and prebuilt rule IDs differ from custom rule IDs in format across Elastic versions. Accepting `str` avoids parse failures on edge-case formats. Validation is advisory (format check only); Pydantic's `UUID` type would reject valid Elastic IDs.

**Why strip volatile fields from the hash:** Elastic's prebuilt rules increment `revision` and `version` whenever Elastic ships an update to its rule library — even for cosmetic changes. If those fields were included in the hash, every Elastic stack upgrade would show spurious drift on every DDR referencing a prebuilt rule. Stripping them means `content_hash` tracks *rule logic* (query, filters, threat mapping), not Elastic's internal bookkeeping.

**Why `entries: []` for complex KQL rather than failing:** A failed export that produces nothing is worse than a warned export that produces an importable skeleton. The engineer sees the MANUAL warning, reviews the `description` (which contains the raw KQL), fills in the entries manually, and imports. The alternative — hard-failing on complex KQL — would block export for the majority of real-world suppression clauses, which tend to be multi-field AND conditions.

**Why `export-elastic-exception`, not `export-elastic`:** The command name is scoped to what it actually produces. A future `export-elastic-query` (for exporting tuned Elastic rule JSON with FP conditions baked in) would be distinct. Naming it `export-elastic-exception` matches Elastic's terminology ("exception lists") and avoids ambiguity.
