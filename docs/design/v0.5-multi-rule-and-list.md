# DDR v0.5 — Multi-Rule Targeting + `ddr list`

**Status:** Plan drafted. Awaiting IMPLEMENT signal.
**Decided:** 2026-05-08
**Theme:** Lock the last schema *shape* change before Elastic/KQL targets land. Ship the read-only `ddr list` command while we're here.

---

## Decision

v0.5 makes two changes:

1. **Multi-rule targeting** — `SigmaTarget` and `SplunkTarget` replace their singular `rule_ref`/`query_ref` field with plural `rule_refs`/`query_refs` lists. A `before`-mode validator provides transparent back-compat for all v0.1–v0.4 records. No new fields, no decision-kind changes.

2. **`ddr list`** — read-only summary command. No schema change. Ships now because it's low-risk, high-utility, and requires iterating over DDR files the same way the new multi-ref `refresh-hash` will.

Out of scope for v0.5: Elastic target (v0.6), KQL targets (v0.7), migration shim (v0.9), schema freeze (v0.9/v1.0).

**Why this order:** Multi-rule is the only remaining schema *shape* change. If it lands after v0.6 and v0.7, two more target model rewrites are needed. Doing it now means Elastic and KQL inherit the plural-refs pattern from day one — no rework.

## 7-Section Plan (locked)

### 1. Refined Goal & Success Criteria

A detection engineer can:

- Author one DDR that suppresses a known FP across three related Sigma rules (e.g. a WMI process-creation, a WMI registry, and a WMI network rule that all fire on the same benign admin tool).
- `ddr new <rule.yml> --decision deprecate` → scaffold with `rule_refs: [{...}]` (a one-element list).
- `ddr validate` on a directory of v0.1–v0.4 single-ref records → all pass unchanged.
- `ddr list detections/` → human-readable summary table by status, target.kind, decision.kind; `--format json` for CI.
- `ddr refresh-hash <multi_ref_ddr.yml>` → iterates all refs, prints per-ref drift, updates all stale hashes in one pass.

Back-compat guarantee: every v0.1–v0.4 record that validated before v0.5 continues to validate after v0.5, with no file edits required.

### 2. Proposed Changes / Feature Breakdown

**Schema (`src/ddr/models/record.py`):**

`SigmaTarget`: `rule_ref: RuleRef` → `rule_refs: list[RuleRef]` (min length 1).

`SplunkTarget`: `query_ref: SplunkQueryRef` → `query_refs: list[SplunkQueryRef]` (min length 1).

Back-compat validator on each target model (`mode="before"`):

```python
@model_validator(mode="before")
@classmethod
def _coerce_singular(cls, data):
    if isinstance(data, dict):
        if "rule_ref" in data and "rule_refs" not in data:
            data = {**data, "rule_refs": [data.pop("rule_ref")]}
    return data
```

Same pattern on `SplunkTarget` for `query_ref` → `query_refs`.

No other model changes. `ddr_version` pattern bumped to accept `"0.5"`.

Cross-field validator (`DDRRecord.check_record_constraints`): `tuning.kind == target.kind` stays. No new cross-field logic needed — the plural refs don't affect it.

**CLI: `ddr list` (new command):**

```
ddr list <path> [--status draft|active|retired] [--target sigma|splunk|elastic|kql-*]
                [--decision suppress|accept-risk|deprecate]
                [--expired] [--due] [--format table|json]
```

- Walks `path` for DDR files (same `_iter_ddr_files` helper as `validate`).
- Silently skips non-DDR YAMLs (same `ddr_version` sniff).
- Prints a compact table: `STATUS | TARGET | DECISION | REFS | ID | TITLE`.
- `REFS` column = number of refs in `rule_refs`/`query_refs`; shows `1` for all existing records.
- `--expired` / `--due` mirror `expire-check` logic but as list filters, not standalone output.
- `--format json` emits a JSON array of record summaries.
- Exit 0 always (read-only — no failure semantics, unlike `expire-check`).

**CLI: `ddr new` (minor update):**

Scaffold output changes: `rule_ref: {...}` → `rule_refs: [{...}]`. Single-element list. No flag changes.

**CLI: `ddr refresh-hash` (update):**

Sigma branch: iterate `target.rule_refs`. For each ref, resolve path (stored `path_or_url` or `--rule` override). Compute new hash. Print per-ref: `refs[0] old: ... new: ...`. Write all updated refs back in one file write. If `--rule` override is provided and `len(rule_refs) > 1`, exit 1 with a clear error ("--rule override cannot be used with multi-ref targets; edit path_or_url in the file directly").

Splunk branch: same iteration over `target.query_refs`. `--conf` override has the same single-ref-only restriction.

**CLI: `ddr validate --strict` (update):**

Drift check iterates all refs. Warns per-ref on drift. Output: `WARN {fp} refs[0]: query_hash drift detected`.

**Examples:**

- Example 08: `examples/08-multi-rule-wmi-deprecate/` — one DDR deprecating three legacy WMI Sigma rules. Files: `sigma-rule-1.yml`, `sigma-rule-2.yml`, `sigma-rule-3.yml`, `ddr.yml`, `README.md`.

**Spec & schema files:**

### 4. Edge Cases & Error Handling

| Case | Handling |
|---|---|
| v0.1–v0.4 YAML with `rule_ref:` (singular) | `before` shim wraps in `[...]` — transparent. |
| v0.5 YAML with `rule_refs: []` (empty list) | Pydantic `min_length=1` → validation error. |
| `ddr new` with `--target sigma` | Scaffold has `rule_refs: [{...}]` (single-element list). |
| `ddr refresh-hash` with `--rule` override on multi-ref DDR | Exit 1: "cannot use --rule override with multi-ref targets." |
| `ddr refresh-hash` with all refs already current | "All hashes unchanged." |
| `ddr refresh-hash` with mixed stale/current refs | Updates stale ones, prints per-ref status for all. |
| `ddr list` on empty directory | "No DDR records found." Exit 0. |
| `ddr list --expired` | Applies expire-check logic as a filter; does NOT exit 1 (unlike `expire-check`). |
| YAML has both `rule_ref` and `rule_refs` | `before` shim: if `rule_refs` present, ignore `rule_ref`. `rule_refs` wins. |
| Multi-ref DDR with >10 refs | `ddr validate --strict` warns: "record has N refs — consider splitting for clarity." |

### 6. Sigma Compatibility & Ecosystem Fit

Multi-rule targeting is purely additive to the DDR schema. The Sigma Filter export path (`ddr export-sigma-filter`) is unaffected — the tuning block is still a single set of selections and a single condition, applied against the rule(s) in `rule_refs`. The filter YAML doesn't change shape.

For the upstream pitch: multi-rule deprecation is a real operational pattern (retiring a cluster of old rules in one governance decision). Showing this in example 08 strengthens the "DDR covers the full lifecycle" story in `docs/upstream-rfc.md`.

The v0.5 plural-refs pattern is the model that v0.6 (`ElasticQueryRef`) and v0.7 (`KqlSentinelQueryRef` etc.) will inherit from the start. This is the schema investment that pays forward.

### 7. Final Plan Summary

v0.5 makes one schema shape change (singular → plural refs on both target kinds) with a `before`-mode coercion shim that makes every v0.1–v0.4 record load unchanged. `ddr new` scaffolds the new shape; `ddr refresh-hash` iterates all refs; `ddr validate --strict` warns per-ref. A new `ddr list` command provides a compact summary view of a DDR directory — no schema involvement, high utility. Example 08 demonstrates a three-rule WMI deprecation. Schema bumps `ddr_version` to accept `"0.5"` and regenerates `spec/ddr-v0.5.schema.json`. No new runtime dependencies. ~25 new tests. Sets up v0.6 (Elastic target) and v0.7 (KQL targets) to inherit the plural-refs shape from the start.

## Architecture notes

**Why `rule_refs: list[RuleRef]` not `targets: list[Target]`:** One DDR governs one decision about one class of detections. A suppress decision with a single tuning block applies the same filter to all referenced rules — the rules must be similar enough that the same FP suppression applies. If you need different tuning per rule, you need different DDRs. This constraint is actually good discipline; making `targets` a heterogeneous list would obscure it.

**`min_length=1` is a hard constraint.** An empty refs list is a schema error, not a warn. DDR has no semantics for "targeting nothing."

**`--rule` and `--conf` override flags are intentionally restricted to single-ref records.** Allowing overrides on multi-ref records requires mapping override paths to specific refs — either by index (fragile) or by ref ID (adds complexity). The correct workflow for multi-ref refresh is to keep `path_or_url` accurate in each ref so `refresh-hash` can find them automatically.
