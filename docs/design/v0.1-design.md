## Part 1 — Initial End-to-End Analysis (Pre-Grilling)

This section preserves the original 7-section thinking process produced at the start of the planning session. Some details were superseded by later decisions; see Part 2 for refinements and Part 3 for the consolidated current state.

### 1.1 Refined Goal & Success Criteria

**Goal.** Ship a minimal, Sigma-native governance layer that lets a detection engineer record *why* a rule was tuned/suppressed/deprecated, version that decision, and export it back into Sigma's existing filter mechanism — without inventing a parallel ecosystem.

**Primary user.** A detection engineer staring at a noisy SigmaHQ rule in their SIEM, wanting to suppress 3 known-benign patterns, document the reasoning, set a 90-day re-review, and not have that decision rot in a Jira ticket or a Splunk macro comment.

**Success criteria (measurable).**
- A new DDR for a noisy rule takes <5 min from `ddr new` to a validated record with an exported Sigma Filter.
- 100% of v0.1 records validate against the published JSON Schema with zero ambiguity.
- Export round-trips: `ddr export-sigma-filter` produces YAML that parses cleanly with `pysigma`.
- 5+ worked examples covering distinct FP archetypes.
- Zero hard dependencies on a database, web service, or non-Python tooling.
- A reviewer reading the README in 10 minutes understands what DDR is, what it is not, and how it relates to Sigma Filters.

**Explicit non-goals (v0.1).** UI, server, web API, multi-tenant storage, RBAC, analytics, integration with specific SIEMs, automated FP detection, ML, custom rule formats.

**Anti-goal.** Becoming "yet another rule format." If a feature could be done in Sigma itself, it does not belong in DDR.

### 1.2 Proposed Changes / Feature Breakdown

Five concentric layers, smallest core out:

**Layer 1 — Spec.**
- `spec/ddr-v0.1.md` — human-readable spec.
- `spec/ddr-v0.1.schema.json` — machine-readable JSON Schema, generated from Pydantic.
- `spec/CHANGELOG.md` — spec changes versioned independently from CLI.

**Layer 2 — Pydantic models (source of truth).**
- `ddr/models/record.py` — `DDRRecord`, `Decision`, `Tuning`, `Lifecycle`, `Provenance`.
- Strict mode on; explicit `extensions` map for forward-compat.

**Layer 3 — CLI (Typer).**
- `ddr new <sigma-rule-path>` — scaffold a record from a Sigma rule.
- `ddr validate <path>` — validate one record or a directory.
- `ddr expire-check <path>` — find records past expiry or due for re-review.
- `ddr export-sigma-filter <path>` — emit a Sigma Filter YAML from a record's `tuning` block.

**Layer 4 — Worked examples.** 5+ DDRs in `examples/`, each pinning a real SigmaHQ rule.

**Layer 5 — Project hygiene.** `pyproject.toml`, `ruff.toml`, pytest config, pre-commit hooks, GitHub Actions CI (lint, test, schema-drift check, example validation), `CONTRIBUTING.md`, `SECURITY.md`, `LICENSE`, `README.md`.

**Build order.** Spec → models → schema export → `validate` → `new` → `export-sigma-filter` → `expire-check` → examples → docs polish.

### 1.3 Initial Schema Shape (superseded — see Part 3)

Top-level groups originally proposed:
- `ddr_version`, `id`, `rule_ref`, `title`, `description`
- `decision` — enum with five values (later revised to three; see Q6)
- `tuning` — Sigma-Filter-shaped block
- `lifecycle` — status + dates (later refined; see Q19)
- `provenance` — author, reviewers, approvals, ticket refs, evidence
- `scope` — environments, data sources, time windows
- `extensions` — `x-*` namespaced free-form map

### 1.4 Edge Cases & Error Handling (initial sketch)

- Rule referenced doesn't exist or commit unreachable.
- Conflicting tunings across multiple DDRs targeting one rule.
- Tuning logic references fields not in the rule's logsource (warn).
- `expires_on` in past on `active` records.
- `ddr_version` mismatch (newer than CLI: hard fail; older: migration shim).
- Filesystem edge cases (Windows paths, symlinks, stdin streaming).
- Security: safe YAML loader exclusively, no `!!python/object`, no network fetch during validate.

### 1.5 Testing Strategy

- **Unit:** Pydantic round-trip, strict-mode rejection, discriminated unions, CLI commands via Typer's `CliRunner`.
- **Integration:** End-to-end on each `examples/` directory; `pysigma` round-trip on exported filters; `expire-check` against fixtures.
- **Schema validation:** Drift test (regenerate schema in CI; fail if checked-in differs); validate every example with both Pydantic and `jsonschema` library; negative corpus in `tests/fixtures/invalid/` covering every failure mode.
- **Cross-platform:** CI matrix Linux + Windows, Python 3.11 + 3.12.
- **Definition of done:** lint clean, tests green both OSes, schema drift check green, all examples validate, CHANGELOG + spec updated.

### 1.6 Sigma Compatibility & Ecosystem Fit

Hard rules:
- **Reference, never embed.** DDR holds the rule's `id` and a path/URL+commit; the rule itself stays in its repo.
- **Field names match Sigma.** `logsource`, `detection`, `selection`, `condition`, `falsepositives` — no renaming.
- **Tuning blocks are Sigma Filter documents.** (Refined in Q11 — now DDR-native, Sigma-Filter-exportable.)
- **Rule IDs are Sigma rule IDs.** UUIDs as Sigma defines them.
- **Backwards compat:** within a major spec version, changes are additive.

**Ecosystem positioning.**
- DDR is *not* a competitor to Sigma's `falsepositives:` field — that's documentation; DDR is governance with lifecycle and exportable suppression logic.
- DDR is *not* a competitor to Sigma Filters — DDR *produces* Sigma Filters and adds the wrapper (who, why, when to revisit).
- DDR is *not* a competitor to ADS writeups — ADS is detection authorship/intent; DDR is post-deployment operational decisions.
- Pitch: *"Sigma Filters answer what to suppress. DDR answers who decided, why, until when, and how to find out if it's still right."*

**Upstream path.** Keep DDR a separate repo and spec until v0.1 has 5+ worked examples and at least one external user. License-align with SigmaHQ from day one (Apache-2.0 leaning).

### 1.7 Final Plan Summary (initial)

DDR v0.1 ships as a Python 3.11+ package with a Typer CLI (`new`, `validate`, `expire-check`, `export-sigma-filter`), Pydantic v2 models that are the source of truth for an exported strict-but-extensible JSON Schema, a human-readable spec, and 5+ worked examples drawn from real noisy SigmaHQ rules pinned by content hash. The format references Sigma rules by ID, uses Sigma's field vocabulary verbatim, and structures its `tuning` block as a serializable Sigma-Filter-compatible IR. Build order: spec → models → schema → validate → new → export → expire-check → examples → docs. CI matrix fails on schema drift, example regression, or cross-platform breakage.

## Part 2 — Grilling Q&A: Locked Decisions and Rationale

Questions raised via `/grill-me`, answers from project lead (Chris), with reasoning preserved for future-self.

### Q1 — Pre- or post-deployment?
**Locked:** v0.1 = post-deployment only. Pre-deployment decisions are a v0.2+ scope.
**Implication:** Lifecycle states stay tight; no `proposed` / `pre-prod` states needed.

### Q2 — One DDR per rule, or 1:N?
**Locked:** Always 1:1. A suppression that applies to multiple rules gets a separate DDR per rule because the reasoning will almost always differ.
**Implication:** `rule_ref` is a single object, not a list. Schema simpler.

### Q3 — Multiple active DDRs per rule?
**Locked:** Yes, allowed (e.g., one suppression for env A, another for env B).
**Implication:** `validate <dir>` does *not* fail on co-targeting. May emit informational report ("rule X has 3 active DDRs in scopes A, B, C") but not a failure. `export-sigma-filter` over a directory will need a story for combining filters per rule (carried forward as sub-question A-bis below).

### Q4 — Sigma-only forever, or multi-format later?
**Locked:** Sigma-coupled for v0.1; multi-format (Splunk-native, Elastic, Panther) in later releases.
**Implication:** **Big structural consequence.** Schema must isolate Sigma-specific bits behind a discriminator from day one. Concretely: `target: { kind: "sigma", ... }` shape, where `sigma` is the only allowed value in v0.1. v0.2 adding `kind: "splunk-native"` becomes additive, not breaking.

### Q5 — Who is the secondary user?
**Locked:** Peer or manager. Not auditor.
**Implication:** Provenance stays lightweight. No SOC2-style controls, no immutable audit log requirements, no schema-enforced "approver must differ from author." `reviewers[]` and `approved_by` are advisory fields, not gates.

### Q6 — `tune` vs. `suppress` distinction?
**Locked:** Collapse `tune` into `suppress`. Decision enum becomes three values.

**Final decision enum for v0.1:**
- `suppress` — exclude known-benign matches via Sigma Filter. Has `tuning` block. The workhorse, expected ~80% of records.
- `accept-risk` — FP exists, not filtered; on-call and downstream consumers know to expect it. No `tuning` block. Required `rationale` and `expires_on` (forces re-review).
- `deprecate` — rule retirement tombstone. Optional `replacement_rule_id`. No `tuning` block.

**Reasoning:** Q11's lock-in (Sigma-Filter-expressible tuning) means `tune` as "rule edit" can't produce a DDR exporter output, and `tune` as "operational throttling" pushes us into multi-target export earlier than v0.1 allows. Two enum values producing identical output guarantees mis-classification. Better: single `suppress` with intent captured in description.

**Dropped from initial taxonomy:**
- `tune` — collapsed into `suppress`.
- `defer` — that's lifecycle status (`draft` with a review date), not a decision.

**Carried forward (open):** Whether to add a `scope.kind: rule-wide | scoped` field or `tags[]` to preserve the rule-wide-vs-scoped governance signal without overloading the decision enum.

### Q11 — Is `tuning` literally a Sigma Filter, or DDR-native?
**Locked:** (c) DDR-native shape that's a strict superset of Sigma Filters, constrained in v0.1 to be losslessly Sigma-Filter-exportable. `target.kind = "sigma"` discriminator shipped in v0.1 even with one valid value.

**Reasoning:**
- Q4 (multi-format later) makes "literal Sigma Filter" a one-way door — would force a breaking change in v0.2.
- Pure DDR-native IR pays full design cost in v0.1 with no second target to validate it against — premature abstraction.
- Hybrid: looks Sigma-Filter-shaped (selections + condition, Sigma field vocabulary), but lives under our discriminator. Schema is *ours*; upstream Sigma Filter churn becomes "update the exporter," not "every existing DDR is invalid."

**v0.1 commitments:**
- `tuning` mirrors Sigma Filter constructs: named `selection` blocks, `condition` string with Sigma semantics.
- Field names follow Sigma vocabulary verbatim — no renaming.
- `export-sigma-filter` is a thin lowering — target <100 lines of real logic.
- Round-trip test in CI: parse known-good Sigma Filter → wrap in DDR → export → assert structural equality.
- **No extension fields in `tuning` that Sigma Filters can't express, in v0.1.** Headroom is reserved, not used.

**Carried forward (open):** Whether to ship at least one DDR-native field (e.g., `scope.environments`, `time_window`) as proof-of-concept, or hold the line at "Sigma-expressible only."

### Q15 — How do we pin a Sigma rule reference?
**Locked:** (c) UUID + content hash. Full-rule hash. `commit` field optional metadata only (not used by validation).

**Reasoning:**
- The question DDR exists to answer is *"is this tuning still safe against the rule as it exists now?"* Content hash answers that directly; commit SHA answers a different question ("what did the author see?").
- Content hash works for internal/private rules with no public commit history.
- Binary changed/unchanged is the right granularity for v0.1 — every change surfaces as "human, go look." Smarter semantic diffing is v0.2+.

**v0.1 commitments:**
- `rule_ref.content_hash` is required: `sha256:...` format, prefix-versioned so future hash algorithms can coexist.
- Canonicalization algorithm pinned in the spec: load with YAML round-trip parser, drop comments, sort mapping keys, normalize line endings (LF), dump UTF-8, SHA-256.
- `rule_ref.commit` is optional, human-readable only — not used by validation.
- `ddr refresh-hash <path>` is a v0.1 sub-command — the safety valve for cosmetic-churn re-reviews. Author re-runs it after confirming nothing semantic changed.

**Accepted tradeoff:** Cosmetic upstream churn (whitespace, comment edits) will trigger re-review nags. Mitigation is `ddr refresh-hash`, not smarter diffing. v0.2+ may scope hashing to `detection:` + `logsource:` blocks if noise proves real.

### Q19 — Lifecycle states?
**Locked:** (d) Stored states are `draft / active / retired`. `expired` and `due-for-review` are computed by the CLI from dates, not stored. `superseded` is a relationship (`superseded_by` field on retired records), not a state.

**Reasoning:**
- Stored states should describe human decisions; computed states describe time-based facts. "This is a draft" is a decision. "This is expired" is what the calendar did to an active record — no one decided it. Conflating means either stale state or CLI-mutates-user-files.
- Three stored values is enough — interesting variation lives in date fields and the `decision` enum.
- `superseded` as a relationship scales better than a parallel terminal state (a retired record can be retired-and-superseded, retired-and-rule-deprecated, or retired-because-FP-source-gone — all under `status: retired`).

**State transitions (three only):**
- `draft → active` (records `activated_on`)
- `active → retired` (records `retired_on`, optional `superseded_by`)
- `draft → retired` (rare: decided not to deploy)

**Lifecycle Pydantic shape:**
- `status` — enum `draft / active / retired`
- `created_on` — required, datetime (RFC 3339)
- `activated_on` — required when `status in {active, retired}` (exception: `draft → retired` direct)
- `retired_on` — required when `status == retired`
- `expires_on` — **required** when `status == active` (no immortal suppressions)
- `review_cadence_days` — optional; if set, `expire-check` flags `last_reviewed_on + cadence < today`
- `last_reviewed_on` — optional, datetime
- `superseded_by` — optional DDR id, only valid when `status == retired`
- `retirement_reason` — optional enum: `rule-deprecated / fp-source-removed / replaced / other`

**`expire-check` behavior:** Returns a computed report (default human-readable table; `--format json` for CI). Rule for "expired": `status == active AND expires_on < today`. Rule for "due for review": `status == active AND last_reviewed_on + review_cadence_days < today`. Optional `--days-ahead N` for lead time on upcoming expiry.

**Defaults locked:**
- `expires_on` required for active records ✅
- `review_cadence_days` shipped in v0.1, optional ✅
- `retirement_reason` enum with `other` escape hatch ✅
- `superseded_by` shipped in v0.1, only valid when retired ✅

### Q26 — Embedded vs. by-reference evidence?
**Locked:** By-reference only. No inline log samples.

**Reasoning:** DDR repos are checked into git. Embedded log samples become a PII/secret leak vector. Schema *prevents* embedding — not just discourages it.

**v0.1 commitments:**
- `evidence[]` items are `{type, ref, note}` only. No `content` / `payload` / `inline` field exists.
- `evidence.type` is a constrained enum: `splunk_query / log_sample_uri / ticket / runbook / dashboard / pcap / other`.
- `evidence.ref` is a string (URL, file path, ticket ID, S3 URI). CLI does not fetch it.
- `evidence.note` is **required**, not optional. If you can't say in one sentence what this evidence shows, it isn't evidence.
- README explicitly states: *"DDRs reference evidence; they don't contain it."*

**Carried forward (open):** Should `validate --strict` lint free-text fields (`description`, `rationale`) for patterns that look like raw log lines (timestamps, IPs, common log delimiters) and warn? Defends the "no inline data" boundary against accidental paste-jobs. Cheap. Default recommendation: yes.

## Part 3 — Consolidated v0.1 State (Post-Grilling)

This is the current source-of-truth design after all locked decisions above.

### 3.1 Decision Taxonomy

Three values, each with distinct operational outcome and exporter behavior:
- `suppress` — has `tuning` block. Exports to Sigma Filter YAML.
- `accept-risk` — no `tuning`. Required `rationale` and `expires_on`. No export.
- `deprecate` — no `tuning`. Optional `replacement_rule_id`. No export, tombstone only.

### 3.2 Schema Shape (current)

Top-level fields of a DDR record:

- `ddr_version` — spec version (e.g., `0.1`). Required.
- `id` — DDR's own UUID. Required, distinct from Sigma rule ID.
- `target` — discriminated. v0.1: `kind: "sigma"` only.
  - `target.rule_ref.rule_id` — Sigma rule UUID.
  - `target.rule_ref.content_hash` — `sha256:...`, computed via canonicalization algorithm v1.
  - `target.rule_ref.source` — enum (`sigmahq / internal / vendor`).
  - `target.rule_ref.path_or_url` — locator.
  - `target.rule_ref.commit` — optional metadata only.
- `title`, `description` — human context.
- `decision` — `suppress / accept-risk / deprecate`. Discriminated union sub-fields per decision.
- `tuning` — present iff `decision == suppress`. Sigma-Filter-expressible IR (selections + condition).
- `lifecycle` — full shape per Q19 above.
- `provenance` — `{author, reviewers[], approved_by, ticket_refs[], evidence[]}`. Lightweight; advisory not gating.
- `scope` — `{environments[], data_sources[]}` (open: should v0.1 even include this if it's not Sigma-Filter-expressible?).
- `extensions` — `x-*` namespaced map.

### 3.3 CLI Surface (v0.1)

- `ddr new <sigma-rule-path>` — scaffold, content-hash the rule, prefill `target`.
- `ddr validate <path-or-dir>` — schema validation; `--strict` enables free-text lint.
- `ddr expire-check <path>` — computed report; `--format json`, `--days-ahead N`.
- `ddr export-sigma-filter <path>` — emit Sigma Filter YAML; only valid for `decision == suppress`.
- `ddr refresh-hash <path>` — recompute and update `target.rule_ref.content_hash` after human-confirmed cosmetic-only change.

### 3.4 Tech Stack (locked in CLAUDE.md)

- Python 3.11+
- Typer (CLI)
- Pydantic v2 (models = source of truth; JSON Schema exported)
- Ruff + Prettier
- Conventional commits + semver
- License: Apache-2.0 (matches SigmaHQ — eases upstreaming)
- File format on disk: YAML (human authoring), JSON for machine pipelines via `--format`

### 3.5 Build Order

1. Spec draft (`spec/ddr-v0.1.md`)
2. Pydantic models
3. JSON Schema export + drift CI
4. `ddr validate`
5. `ddr new`
6. `ddr export-sigma-filter`
7. `ddr expire-check`
8. `ddr refresh-hash`
9. Worked examples (5+)
10. Docs polish

## Part 4 — Open Items (Pending Decision)

Carried forward, blocking nothing critical but should be resolved before IMPLEMENT:

2. **Q11 carry — DDR-native field in v0.1?** Ship at least one field that Sigma Filters can't express (e.g., `scope.environments`, `time_window`) as proof-of-concept, or hold the line at "Sigma-expressible only"?
3. **Q26 carry — free-text lint.** Should `validate --strict` warn on patterns in `description` / `rationale` that look like raw log lines?
4. **Q19 carry — combined export behavior.** When `export-sigma-filter` runs over a directory and finds N active DDRs for the same rule (Q3), does it: (a) combine into one Sigma Filter doc per rule, (b) emit separate filter files, (c) require `--combine` flag? Recommendation: (b).
5. **Q41 — worked examples.** Which 5 SigmaHQ rules become the canonical examples? Recommendation: process_creation (admin tool), Zeek/network, Windows event log, cloud, plus one `accept-risk` and one `deprecate` to exercise non-suppress branches.
6. **Examples vendored vs. referenced.** Vendored fits content-hash pinning naturally; recommendation: vendor the rule YAML alongside each example.
7. **Decision enum trimming.** Confirm three values is the right count, or trim further (e.g., drop `accept-risk` to v0.2).
8. **Library API.** Ship `from ddr import DDRRecord` as a public contract in v0.1, or CLI-only?
9. **CI matrix.** Add macOS? Add Python 3.13?
